## Rules that apply to every task

| Rule     | Detail                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------- |
| Branch   | One task per branch, `<type>/<scope>-<slug>`, from `main`. Never commit on `main`.                              |
| PR       | Required. State problem, scope, non-goals, security impact, compatibility, evidence, rollout, unresolved risks. |
| Evidence | A passing command is not acceptance. State what behaviour you verified and what you could not.                  |
| Live DB  | Tasks touching persistence, RLS or tenancy need a migrated database. Bootstrap below.                           |
| Honesty  | Use `implemented` / `partial` / `absent` / `unverified`. Never claim closed on hope.                            |
| Scope    | Do not fix unrelated defects you find. Open a separate branch and note it.                                      |

## Model assignment

A heuristic, not a hard rule. Reassign freely.

  the target shape is already visible in the repo.
- **Grok** — tasks whose difficulty is deciding _what_ correct means: architecture,
  security reasoning, contract design, or reconciling conflicting sources of truth.

## Sequencing

Dependencies matter more than priority order.

```text
10 (unblocks local setup)
 ├─ 1  payment ─┐
 ├─ 2  sms/email ┤→ product can transact
 ├─ 4  tenant source of truth → 3 tenant suspension
 ├─ 7  document-store backstop → 8 billing scope
 ├─ 5  live tests (health, auth)
 └─ 9  report artefacts
       └─ 6 deploy  (last: it measures everything above)
```

Task 4 should land before 3, because fixing the source of truth changes what 3
should read. Task 7 before 8, because 8 becomes trivial once scoped methods exist.
Task 6 last, since its value is measuring the rest.

## Caveat for whoever executes this

Only 2 of 39 modules have had a deep evaluation, and 28 of 39 have no live database
proof. Tasks 1–4 and 7–10 are grounded in verified evidence. Tasks 5 and 6 are the
ones that will change this sheet: once modules are proven against a live database
and something is actually deployed, expect gaps to surface that rank above items on
this list. Treat the ordering as current best knowledge, not settled.
