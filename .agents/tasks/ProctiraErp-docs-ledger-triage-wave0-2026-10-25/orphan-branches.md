## Method

Everything ran against `/home/ec2-user/ProctiraErp/.agents/worktrees/ledger-triage-wave0` with read-only git. Scratch data lived in `/tmp/ob-w0`; temporary objects were redirected there with `GIT_OBJECT_DIRECTORY`, so the repository object store was not written to.

```bash
git rev-parse -q --verify refs/heads/<b>; git rev-parse -q --verify refs/remotes/origin/<b>
git merge-base origin/main <b>; git rev-list --left-right --count origin/main...<b>; git log -1 --format=%ci <b>
git cherry -v origin/main <b>                 # patch-id equivalence (git patch-id --stable semantics)
git log --format=%B origin/main               # squash bodies: '* <subject>' bullets per merged commit
git show --format= --no-renames <sha>         # per-commit added/removed lines
git diff --no-renames $(git merge-base origin/main <b>) <b>   # net branch delta
git show origin/main:<path> / git show <b>:<path>              # tip content comparison
git grep -n -F/-E <marker|identifier> origin/main -- <paths>   # semantic presence checks
git rev-list 3161a14b; git merge-base --octopus <big branches>  # shared-stack structure
git diff --name-only origin/main...<in-flight branch>          # in-flight overlap
```

main is squash-merged, so 0 commits match by patch-id (`git cherry` reported 0 `-` for every branch) and `range-diff` against a squash is not meaningful. Each '+' commit was therefore judged by:

1. Subject match against every subject and `* bullet` line in main commit messages (the squash bodies list the merged commits).
2. Content containment. Each significant added line that survives at the branch tip is checked for in the main version of the same file. Removed lines are checked for still being on main. Files absent on main are reported separately.
3. For commits that fail both tests, a whole-tree `git grep` probe of distinctive missing lines and PRC markers, then manual semantic checks of the behaviour on main (cited per commit below).

Dispositions come from `docs/audits/remediation/CANONICAL_LEDGER.csv`. It holds only PRC-L and PRC-M ids (758 rows), so every PRC-H and PRC-C id is `NOT_IN_LEDGER`, as are many L ids (for example L023, L034, L232, L241, L579).
